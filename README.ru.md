# @hoshinotatsuya/pg-replica-sync

[![npm](https://img.shields.io/npm/v/@hoshinotatsuya/pg-replica-sync.svg)](https://www.npmjs.com/package/@hoshinotatsuya/pg-replica-sync)
[![CI](https://github.com/HoshinoTatsuya/pg-replica-sync/actions/workflows/ci.yml/badge.svg)](https://github.com/HoshinoTatsuya/pg-replica-sync/actions/workflows/ci.yml)

[English](README.md) · [Изменения](CHANGELOG.md)

Чтение с реплики Postgres с гарантией «читаешь свои записи» (read-your-writes) по позиции WAL. После записи клиент получает подписанный токен позиции. Чтение с этим токеном уходит на реплику, только если доказано, что она воспроизвела эту позицию на той же линии времени того же кластера. Иначе чтение уходит на мастер. Всё, что не удалось установить, тоже отправляет чтение на мастер, а не на реплику.

Поддерживается Postgres 15–18: полный набор спек проходит на postgres:15, 16, 17 и 18 (`PG_TEST_IMAGE`). Младше 15 не поддерживается и не проверяется.

## Когда это нужно, а когда нет

**Нужно**, если чтения уже идут на реплики (асинхронная потоковая репликация) и пользователь, только что что-то записав, не должен увидеть старое: сохранил профиль, обновил страницу, а изменения нет. Это классический дефект «чтения с реплики». Обычно его лечат либо «все чтения после записи — на мастер на N секунд» (угадывание, которое ломается при отставании больше N), либо «все чтения на мастер» (тогда реплики не разгружают мастер).

**Не нужно:**
- **без реплик**. Если всё читается с мастера, «читаешь свои записи» выполняется и так, а пакет только добавит зонды;
- при синхронной репликации с `synchronous_commit = remote_apply`: коммит и так ждёт применения на синхронной реплике (ценой задержки каждой записи);
- если чтению достаточно «не старше N секунд» без привязки к своей записи. Тогда хватает чтения без токена с потолком отставания (ниже), а токены не нужны.

## Установка

```sh
pnpm add @hoshinotatsuya/pg-replica-sync pg
pnpm add -D @types/pg   # необязательно, для TypeScript
```

Peer-зависимости: `pg` `^8.18.0`, `@types/pg` `>=8.15.0` (необязательна); других зависимостей в рантайме нет. Node.js ≥ 24. Роли зонда нужно членство в `pg_monitor` или `pg_read_all_stats` (см. «Права роли зонда»).

## API

```ts
import { ReplicaRouter } from '@hoshinotatsuya/pg-replica-sync';
import { Pool } from 'pg';

/** A required environment variable: missing means a startup failure, not `undefined` in the options. */
const required = (key: string): string => {
  const value = process.env[key];
  if (value === undefined || value === '') {
    throw new Error(`${key} is not set`);
  }
  return value;
};

const primaryPool = new Pool({ connectionString: required('PRIMARY_URL') });
const replica1Pool = new Pool({ connectionString: required('REPLICA1_URL') });
const replica2Pool = new Pool({ connectionString: required('REPLICA2_URL') });

export const router = new ReplicaRouter<Pool>({
  // `connection` is what the router's own probe connects to; `target` is what you read with.
  primary: { name: 'primary', connection: required('PRIMARY_URL'), target: primaryPool },
  replicas: [
    { name: 'r1', connection: required('REPLICA1_URL'), target: replica1Pool },
    { name: 'r2', connection: required('REPLICA2_URL'), target: replica2Pool },
  ],
  // >= 32 RANDOM bytes (openssl rand -base64 32); to rotate, put the new key first
  secrets: [required('REPLICA_TOKEN_KEY')],
});

// Write: COMMIT and the token in one call, on the transaction's own connection.
export async function renameProfile(id: number, name: string): Promise<string> {
  const client = await primaryPool.connect();
  try {
    await client.query('BEGIN');
    await client.query('UPDATE profiles SET name = $1 WHERE id = $2', [name, id]);
    return await router.commitAndIssueToken(client); // give it to the client: a cookie, a header
  } catch (error) {
    // An exception means "no write, or unknown": end the transaction HERE, otherwise the connection
    // goes back to the pool with an open transaction and somebody else's COMMIT commits it.
    await client.query('ROLLBACK').catch(() => undefined);
    throw error;
  } finally {
    client.release();
  }
}

// Read: with the token of the client's last write (undefined when there is none).
export async function loadProfile(id: number, token: string | undefined) {
  const { target, role, reason } = await router.route(token);
  const { rows } = await target.query('SELECT * FROM profiles WHERE id = $1', [id]);
  return { rows, servedBy: role, reason }; // role: 'primary' | 'replica'
}
```

Каждый блок `ts` этого README и README.md (они одинаковы) компилирует спека `readme-examples.spec.ts` под `strict`, `exactOptionalPropertyTypes` и `noUncheckedIndexedAccess` против исходников пакета; объекты приложения, которых блок не объявил сам (пулы, `router`, `token`, `work`, …), объявляет её пролог.

`target` — то, чем вызывающий читает с узла (пул `pg`, drizzle, что угодно). Пакет его не трогает. Состояние узлов снимается **своими** соединениями зонда, по одному на узел: зонд можно оборвать по потолку времени, не трогая пул приложения. `router.close()` (или `await using`) закрывает только их.

**После `close()`** новый `route()` — исключение (чтение ещё не начато). Начатое до закрытия не роняется: идущие `route()` решают «мастер» по тому, что уже знают; `issueToken` и `commitAndIssueToken` дают токен «только мастер» (COMMIT `commitAndIssueToken` отправляется как обычно — запись не остаётся висеть открытой транзакцией); `confirm` — `false`, чтение с мастера.

**Ключ подписи** — случайные байты, не меньше 32 (`openssl rand -base64 32`). При создании отвергается ключ, который подбирается перебором по форме: повторение куска (`'k'.repeat(32)`, `'ab'.repeat(16)`, нулевой буфер), мало разных байтов (эмпирическая энтропия гистограммы меньше 64 бит на ключ: `'a'×31+'b'`, `'0'×63+'1'`), почти-повтор (deflate сжимает ключ меньше чем до 128 бит: `'abcdefgh'×4` с одной заменой). Случайные ключи проходят с запасом (20 000 ключей каждой формы — 32 байта, hex от 16 байт, base64 от 24 байт — минимум 93 бита по гистограмме и 240 после сжатия). **Граница:** словарный ключ, ключ из пароля, перебор алфавита (`'abcdefghijklmnopqrstuvwxyz012345'`) этой проверкой не обнаруживаются — энтропию строки по самой строке не измерить. Проверка линейна по длине ключа (длинный ключ из настройки не вешает старт).

### Токен после записи

Токен обязан взять позицию **после** COMMIT, иначе он меньше позиции коммита, и реплика «догонит» его без этой записи. Поэтому соединение передаётся всегда, и есть два способа:

- **`commitAndIssueToken(client)`** — COMMIT на соединении транзакции и позиция с него же: порядок держит пакет. До COMMIT проверяется инвариант «на ЭТОМ соединении открыта транзакция» — `SAVEPOINT`: вне транзакции Postgres отвечает отказом (25P01), и тогда `TransactionNotOpenError`, а COMMIT не отправляется вовсе. Так отсекается пул и любая обёртка над ним (`{ query: (t) => pool.query(t) }`): на случайном соединении COMMIT прошёл бы с предупреждением «нет транзакции» и тегом `COMMIT`, токен был бы выдан, а настоящая транзакция осталась бы открытой — реплика проходила бы токен без записи. Запись без `BEGIN` (каждый оператор сам себе транзакция) — тоже `TransactionNotOpenError`: для неё — `issueToken(client)`. Транзакция с ошибкой (`SAVEPOINT` отвечает 25P02) завершается `ROLLBACK` — `TransactionNotCommittedError`, токена нет, соединение без транзакции. Отказ самого COMMIT — его исключение. SQLSTATE ищется и в цепочке `cause`: обёртка слоя доступа, переносящая отказ драйвера в `cause`, опознаётся так же (без этого — повторный бросок и пул, отравленный транзакцией «current transaction is aborted»).

  Любое исключение `commitAndIssueToken` значит «записи нет или неизвестно, что с ней», и транзакцию завершает вызывающий (`catch → ROLLBACK`, как в примере): иначе соединение возвращается в пул с открытой транзакцией, следующий запрос из пула получает её («there is already a transaction in progress»), и его COMMIT закоммитит запись запроса, которому ответили ошибкой (воспроизведено). После того как COMMIT прошёл, исключений нет: токен с позицией или «только мастер». Поэтому:
  - закрытый маршрутизатор (`close()` раньше, чем допиты запросы при выключении) COMMIT не отменяет — COMMIT как обычно и токен «только мастер»;
  - драйвер, который не сообщает тег ответа (`command`), после COMMIT исправной транзакции получает токен, а не «откачена»: исправность проверена `SAVEPOINT` до COMMIT, и «откачена» при прошедшей записи толкала бы к повтору — дубль;
  - пул в `commitAndIssueToken` не принимается и типом (`NotAPool`: у `pg.Pool` есть счётчики соединений); обёртку `{ query }` тип не отличит — её отсекает рантайм.
- **`issueToken(executor)`** — когда COMMIT делает кто-то другой (ORM, `transaction(...)`): вызывать ПОСЛЕ того, как COMMIT вернулся, с соединением, на котором он прошёл, или с любым соединением мастера (пулом): позиция вставки монотонна, и после COMMIT она не меньше его конца. Если на ЭТОМ соединении открыта транзакция с записью, токен «только мастер» (`write_pending`). Транзакцию ДРУГОГО соединения пакет не видит: `issueToken(pool)` до того, как COMMIT вернулся, даст токен меньше коммита, и это не обнаружить ничем. Поэтому, где можно, — `commitAndIssueToken`.

Без аргумента `issueToken()` — `TypeError`: в 0.1 он брал позицию своим соединением зонда, которое транзакцию вызывающего не видит (вызов внутри транзакции давал токен без записи), и все токены процесса шли через одно соединение.

`issueToken` не бросает на отказах узла. Если позицию определить не удалось (узел в recovery, незакоммиченная запись на этом соединении, отказ, потолок времени `probeTimeoutMs`, маршрутизатор закрыт), выдаётся токен «только мастер»: клиент с ним читает с мастера (`reason: 'token-unresolved'`, хук `tokenUnresolved`), пока не получит новый токен при следующей записи. Такой токен не стареет: его позиция неизвестна, и «как без токена» могло бы отправить чтение на реплику с задержкой применения, которая укладывается в потолок отставания, но записи не видела. Потолок времени `issueToken` и `confirm` не отменяет запрос на соединении вызывающего: оно занято до ответа сервера.

Позиция в токене — `pg_current_wal_insert_lsn()`, а не `pg_current_wal_lsn()`. При `synchronous_commit = off` запись коммита может быть ещё не записана в WAL, и позиция записи окажется меньше конца коммита (замер: 300 из 300 токенов). Позиция вставки всегда не меньше. Если позиция вставки стоит сразу за заголовком страницы WAL (последняя запись кончилась ровно на границе страницы или сегмент только что переключён), токен берёт саму границу: на странице ещё нет ни одной записи, а реплика воспроизводит ровно до границы. Размеры заголовков — из раскладки сервера (`pg_control_init()`), не определилась — позиция вставки как есть.

### Узел-балансировщик

Адрес узла должен вести на **один** сервер: зонд доказывает состояние того сервера, к которому подключён. Если адрес — балансировщик над несколькими репликами (сервис «только чтение» в Kubernetes, прокси, читающая точка облака), зонд видит один сервер, а чтение попадает на любой — и без подтверждения 5 из 10 чтений не видели запись (замер). Такой узел помечается `balanced: true`; решение по нему приходит с `mustConfirm: true`, и подтверждается **на соединении чтения**:

```ts
const decision = await router.route(token);
const client = await decision.target.connect();
try {
  // `confirm` runs the same probe on THIS connection; `false` means read from the primary.
  const reader = (await router.confirm(decision, client)) ? client : primaryPool;
  await reader.query('SELECT 1');
} finally {
  client.release();
}
```

`confirm` выполняет тот же зонд на соединении чтения и проверяет те же условия, поэтому роли ЧТЕНИЯ нужны те же права, что роли зонда (`pg_monitor` или `pg_read_all_stats`): без них линия времени сервера чтения не видна, и подтверждения нет. Отказ, потолок времени, «не смогли определить» — `false`. Решение «мастер» подтверждать не нужно (`true`). Итоги видны: `stats().confirms` (подтверждено, отклонено и почему) и хук `observer.confirmed` — решение «реплика», отклонённое здесь, в `reads.replica` уже посчитано, а чтение ушло на мастер. Цена — один запрос на чтение: кэш здесь невозможен, соединения чтения ведут на разные серверы. Пакет сам не отличает балансировщик от одного сервера — пометка на совести настройки.

Подтверждение доказывает состояние сервера, на котором выполнено, — значит, чтение обязано идти на ТОТ ЖЕ сервер. Балансировщик по соединениям (TCP, сервис Kubernetes, `pgbouncer` в режиме session) это обеспечивает: соединение привязано к серверу. Пулер в режиме transaction (`pgbouncer` над несколькими серверами, `pgpool`) привязывает к серверу только транзакцию: `confirm` вызывать ВНУТРИ читающей транзакции, первым запросом после `BEGIN`, и читать в ней же (проверено спекой на pgbouncer 1.26 над двумя репликами). Режим statement (каждый запрос — на любой сервер) не поддерживается: подтверждать там нечего.

## Как выбирается узел

**С токеном** реплика подходит, только если установлено **каждое** условие ниже. Иначе она исключается с причиной (`EXCLUSION_REASON`):

| Условие | Как узнаётся | Не так → причина исключения |
|---|---|---|
| зонд ответил в потолок времени | своё соединение, `probeTimeoutMs` | `unavailable` |
| узел — реплика | `pg_is_in_recovery()` | `promoted` |
| воспроизведение не на паузе | `pg_get_wal_replay_pause_state()` | `paused` |
| тот же кластер | `pg_control_system().system_identifier` | `other-cluster` / `state-unknown` |
| та же линия времени | `pg_stat_wal_receiver.received_tli` (приёмник стоит — см. ниже) | `timeline-mismatch` / `timeline-unknown` / `no-stats-privilege` |
| догнала позицию | `pg_last_wal_replay_lsn() ≥ позиция токена` | `behind` |

Позиции сравниваются как 64-битные числа (`X/Y` → `X·2³² + Y`). Строкой сравнивать нельзя: `'10/0' < '9/0'` лексикографически. `parseLsn`, `formatLsn`, `compareLsn` экспортируются.

Если подходящих реплик несколько, чтения раздаются по кругу. Если ни одна не подошла, чтение идёт на мастер. Причина (`ROUTE_REASON`) уточняется по состоянию мастера: `token-other-timeline` (у мастера другая линия, был failover), `token-ahead-of-primary` (позиция токена впереди мастера той же линии: токен «из будущего»), `token-foreign` (другой кластер), иначе `no-replica-eligible`. «Впереди мастера» называется только по зонду мастера, начатому ПОСЛЕ первой встречи процесса с позицией токена: токен с этой позицией выдан раньше, и к началу такого зонда позиция вставки мастера (если он не сменился) не меньше её; мастер, снятый раньше, законно позади (без этого свежий законный токен давал ложное `token-ahead-of-primary` в 556 чтениях из 2000). Зонд, уже идущий с более раннего момента, тоже не годится: его дожидаются и зондируют снова. Нет такого зонда (потолок времени, отказ) — `no-replica-eligible`. Испорченный, обрезанный, подписанный чужим ключом, прежней версии (`v1`) или слишком длинный (> 256 символов) токен даёт `token-invalid` и чтение с мастера. Такой токен не роняет запрос и не уводит его на реплику.

**Потолок времени.** `route()` длится не дольше `probeTimeoutMs + waitForCatchUpMs` (плюс время цикла событий; зонд, начатый до первой встречи с позицией и ещё идущий, дожидается в том же потолке). Первый зонд ограничен своим потолком, опросы во время ожидания и зонд мастера для причины — остатком; зонд, не успевший к потолку, не ждётся (он доживает до своего потолка и попадает в кэш), а реплика в этом решении — с прежней оценкой или `unavailable`. Без этого медленная реплика и замёрзший мастер давали 2.4–2.8 с при обещанных 1.5.

**Ожидание догоняния** (`waitForCatchUpMs`, по умолчанию 0). Если реплики только отстают (`behind`), чтение опрашивает их каждые `catchUpPollMs` (но не чаще `minProbeIntervalMs`) до потолка и уходит на первую догнавшую. Реплики на паузе, недоступные и с другой линией времени не ждутся.

**Без токена** (`route()` / `route(undefined)` / пустая строка) реплика подходит при тех же условиях, только вместо «догнала позицию» проверяется «отстаёт от позиции вставки мастера не больше `maxLagBytes`» (по умолчанию 1 МиБ). Линия времени сверяется с линией мастера. Если состояние мастера не определилось (недоступен, в recovery), чтение уходит на мастер (`primary-state-unknown`): отставание без мастера не измерить. Отставание меряется в байтах WAL, а не секундами `now() - pg_last_xact_replay_timestamp()`: на простаивающем мастере такие секунды растут без всякого отставания. Обратное тоже верно: реплика с `recovery_min_apply_delay` может отставать на час и укладываться в потолок байтов — такие реплики для чтения без токена не годятся.

**Срок жизни токена** (`tokenTtlMs`, по умолчанию 60 с; момент выдачи — в токене, по часам `wallClock` выдавшего процесса). Токен, который после failover или подмены кластера не выполнит ни одна реплика, — другой линии времени (`token-other-timeline`), другого кластера (`token-foreign`), впереди мастера той же линии (`token-ahead-of-primary`), — держит чтения на мастере только `tokenTtlMs`; старше — чтение как без токена, счётчик `stats().expiredTokens`. Без срока такие клиенты после failover сидели на мастере до своей следующей записи.

Истекает только **доказанно** невыполнимый токен: причина установлена состоянием мастера из зонда, начатого после первой встречи процесса с позицией токена (или каждая реплика — другой кластер). Кэш мастера, снятый раньше, ничего не доказывает: свежий законный токен впереди него законно. В 0.2.0 до исправления истечение шло по любому кэшу мастера моложе `stateTtlMs`, и при часах читателя на 120 с впереди законный свежий токен «истекал», а чтение уходило как без токена на реплику с задержкой применения, где записи нет (воспроизведено: до 39 из 40 чтений, и при совпадающих часах с `tokenTtlMs: 1` — 14 из 40). Теперь для просроченного токена зонд мастера идёт, даже если кэш говорит «позади», — один на позицию (дальше кэш с тем же доказательством), так что под нагрузкой невыполнимый токен по-прежнему истекает. Токен «только мастер» (`token-unresolved`) НЕ стареет (выше), токен своей линии времени, сколько бы ему ни было, проверяется по позиции: эта проверка точна и дешева, и «как без токена» было бы слабее.

Расхождение часов процессов. Возраст токена — разность часов читателя и выдавшего, и расхождение сдвигает **только срок невыполнимого токена**: часы читателя впереди на X — такой токен истекает на X раньше (на `tokenTtlMs` и больше — сразу), позади — позже. Законный токен своей линии ни при каком расхождении и ни при каком `tokenTtlMs` не истекает: истечение требует доказательства, а не возраста (спека `expiry-proof.db.spec.ts`: часы читателя ±120 с, `tokenTtlMs` 1 и 200, кэш мастера снят до записи, идущий зонд мастера — каждое чтение на мастер, запись видна). Поэтому соотношение `tokenTtlMs` с `stateTtlMs` и потолками зонда на старте не проверяется: оно больше ни на что не влияет.

## Кэш состояния и цена

Каждое решение опирается на состояние узлов. Если снимать его на каждое чтение, это лишний запрос на чтение (зонд — один запрос, `PROBE_SQL.STATE`). Поэтому состояние кэшируется:

- запись кэша живёт `stateTtlMs` (250 мс, не больше 1000) и **выселяется** при каждом обращении, а не только перестаёт читаться. Ключи — только узлы из настройки, так что кэш не растёт ни со временем, ни от ввода;
- с токеном сначала смотрится только кэш. Реплика, догнавшая позицию по кэшу, используется без зонда. Свежий зонд идёт только к репликам, отстающим по кэшу или отсутствующим в нём;
- позиция воспроизведения реплики **убывает** при перезапуске: она откатывается к minRecoveryPoint (замер: на 69–94 МБ сразу после старта). Поэтому соединение зонда, оборванное не по воле пакета (перезапуск сервера, обрыв сети), сразу выселяет узел из кэша, и следующее чтение решает по свежему зонду. Если обрыв до клиента не дошёл (сеть молчит), старое состояние живёт до `stateTtlMs` — отсюда его потолок 1 с;
- реплика, которая по зонду, начатому ПОСЛЕ первой встречи процесса с позицией этого токена, отстаёт, зондируется снова не чаще `minProbeIntervalMs` (10 мс), при любом числе чтений с этой позицией. Без этого токен впереди отставших реплик стоил по свежему зонду каждой реплики на каждое чтение (замер аудита: 1842 зонда в секунду при 50 параллельных чтениях). Зонд, начатый раньше первой встречи с токеном, о его записи ничего не говорит, поэтому чтение сразу после своей записи получает свежий зонд и в пределах потолка (одновременные чтения по-прежнему ждут один зонд). Сравниваются номера зондов, а не часы: расхождение часов процессов потолок не снимает и чужой зонд не отдаёт. Помнится **позиция**, а не строка токена: токены одной позиции (разные моменты выдачи) делят запись. Маршрутизатор помнит до 1024 позиций (`POSITION_MEMORY`: ключи приходят от клиентов), вытесняется давно не встречавшаяся (LRU), так что позиция, которую читают, при потоке новых не уходит; вытесненная при новой встрече считается новой — один лишний зонд каждой реплики, после чего снова помнится. Граница: больше 1024 РАЗНЫХ позиций, читаемых по кругу, — каждое чтение как с новым токеном (свежий зонд каждой реплики; одновременные чтения его делят). Замер аудита до исправления (память по строке токена, вытеснение по порядку вставки): 2000 токенов по кругу — 2384 зонда/с против 200/с у одного токена; спеки: 2000 токенов на 100 позиций дважды по кругу — ровно по 100 зондов каждой реплики, горячая позиция среди 2048 новых — ни одного лишнего зонда. `minProbeIntervalMs: 0` — без потолка;
- если зонд не ответил, отказ живёт `unavailableRetryMs` (2 с). Недоступная или замёрзшая реплика задерживает на `probeTimeoutMs` одно чтение в этом окне, а не каждое;
- зонд, не уложившийся в `probeTimeoutMs`, — отказ этого зонда, но соединение зонда не рвётся до `connectTimeoutMs` (10 с) с начала установки или запроса. Медленная, но живая реплика, у которой установка соединения (несколько обменов) дольше потолка зонда, а запрос — короче, так получает готовое соединение к следующему зонду (было: соединение рвалось на потолке зонда, следующий зонд начинал установку заново, и реплика с RTT 360 мс была `unavailable` навсегда — 20 из 20 решений за 6 с). Замёрзшая реплика не отвечает и к `connectTimeoutMs`: она остаётся `unavailable`, соединение рвётся и открывается заново (спека: и то, и другое через `FaultProxy`);
- часы кэша — опция `clock` (по умолчанию `performance.now`). Часы, шагнувшие назад (NTP, часы стенда), выселяют весь кэш: потолок записи отсчитан по прежним часам, и после шага на час назад она жила бы лишний час — пауза реплики не замечалась (воспроизведено: 10 из 10 решений «реплика» за секунду после паузы). Не-число — тоже выселение, и записи не кладутся; часы, не дающие конечного числа уже при создании, — `InvalidReplicaSyncOptionsError`;
- одновременные чтения ждут один зонд узла, а не шлют свои.

Замер `bench/cost.cjs` (0.2.0; мастер и 2 реплики postgres:17 в docker на ноутбуке, роль приложения):

| Сценарий | Зондов на чтение | Цена `route()` |
|---|---|---|
| чтение по ключу с реплики (для сравнения) | — | p50 0.19 мс, p99 0.95 мс |
| сам зонд (`PROBE_SQL.STATE`) | — | p50 0.26 мс, p99 0.79 мс |
| тот же токен, 5000 чтений подряд (в пределах потолка кэша) | 0.0004 (2 зонда) | p50 0.006 мс |
| тот же токен, 2000 чтений за 2.4 с | 0.010 (8 зондов/с = 2 реплики × 4 потолка кэша в секунду) | — |
| без токена, 5000 чтений | 0.0006 (3 зонда: мастер + 2 реплики) | p50 0.001 мс |
| запись → чтение с **новым** токеном, 1000 раз | **2.0** (каждая реплика, параллельно); на реплику 999 из 1000 | запись + токен + route: p50 1.1 мс |
| реплики отстают, 50 параллельных потоков читают с одним токеном 2 с | 0.0018: **203 зонда/с** на 2 реплики (без потолка частоты — 2647/с) | — |
| без кэша (`stateTtlMs: 1`), 1 реплика | 1.0 | +1 зонд ≈ +0.3 мс к чтению 0.2 мс |

Отсюда: лишний запрос на чтение — это сценарий «чтение сразу после своей записи» (позиция свежего токена впереди кэша), и тогда зондируются **все** реплики сразу. Когда реплики отстают, повторные чтения с тем же токеном зондируют каждую реплику не чаще раза в `minProbeIntervalMs` — то есть до 100 зондов в секунду на узел при любом числе чтений, а не на каждое чтение. На остальных чтениях кэш сводит цену к нескольким зондам в секунду на узел. 999 из 1000 чтений сразу после записи ушли на реплику: локальная репликация догоняет быстрее, чем идёт зонд. На реальной сети доля мастера выше, и `waitForCatchUpMs` в несколько миллисекунд обычно возвращает такие чтения на реплику.

## Граница гарантии

- **Читаешь свои записи — для того, кто несёт токен.** Чтение с токеном видит всё, что было закоммичено до выдачи токена (в пределах кластера и линии времени токена). Чужие записи, сделанные после, могут быть ещё не видны. Это не линеаризуемость и не «последнее значение»: за ним — на мастер.
- **Причинность между клиентами — только через передачу токена.** Если сервис A записал и передал токен сервису B (в сообщении, заголовке), B прочтёт не старее. Без токена B получает только «отставание не больше `maxLagBytes`».
- **Монотонность чтений — относительно своей позиции.** Два чтения с одним токеном могут уйти на разные реплики, и вторая может быть позади первой (но не позади токена). Нужна монотонность между чтениями — продвигайте токен: выдавайте новый после чтения (`issueToken(pool)`) или держите одну реплику.
- **Токен, взятый до COMMIT на ДРУГОМ соединении, не обнаруживается** (см. «Токен после записи»). `commitAndIssueToken` этого не допускает.
- **Узел-балансировщик без `balanced: true` не обнаруживается**: решение доказано про сервер зонда, а не про сервер чтения. Пулер в режиме statement не поддерживается (см. «Узел-балансировщик»).
- **Реплика, которая при стоящем приёмнике WAL перешла на новую линию времени из архива** (`restore_command`), получает прежнюю линию времени своего экземпляра (см. «Failover и недоступный мастер»). Переход на новую линию — это failover: запись, потерянная при нём, не видна и на новом мастере. Спекой не воспроизведено.
- **Потолок кэша — окно, в котором узел может поменять роль незаметно**, если обрыв соединения зонда до клиента не дошёл. Реплика, догнавшая токен по кэшу, используется до `stateTtlMs` даже после промоции. Это безопасно для «своих записей» (данные до позиции на ней есть), но для `paused`, недоступности и перезапуска (откат позиции воспроизведения) решение опаздывает на тот же потолок, не больше 1 с.
- **Две промоции на один номер линии времени (раздвоение истории) не различаются.** Если две реплики одного мастера промотированы независимо, обе выходят на линию N+1, и токен линии N+1 одного мастера засчитывается реплике, следующей за другим (замер: запись невидима, решение «реплика»). Различить ветви по `system_identifier` и номеру линии нельзя, а файлы истории линий при одной точке ветвления совпадают байт в байт — признака, доступного роли зонда, нет. Два мастера одновременно — отказ оркестратора (fencing), и пакет его не лечит.

## Failover и недоступный мастер

- **Реплика стала мастером** (`pg_promote`, переключение). Зонд видит `pg_is_in_recovery() = false`, и узел исключается как `promoted` и для чтений с токеном, и без него. Проверено на настоящей промоции.
- **Мастер недоступен реплике** (лежит, сеть): приёмник WAL реплики стоит, `received_tli` пуст. Линия времени тогда берётся та, что приёмник показывал у **этого же экземпляра** реплики (экземпляр — `system_identifier` и момент старта postmaster: после перезапуска знание не переносится), и чтение с токеном, который реплика воспроизвела, идёт на неё, а не на лежащий мастер. Сменить линию времени реплика может, только последовав за новым мастером, то есть после failover: запись, потерянная при нём, не видна и на новом мастере. Маршрутизатор, ни разу не видевший линию времени реплики, её не угадывает (`timeline-unknown`). Чтение **без** токена при недоступном мастере идёт на мастер (`primary-state-unknown`): отставание без него не измерить.
- **Токен со старой линии времени после failover.** Новый мастер на линии N+1, токены выданы на линии N. Чтения с ними идут на мастер (`token-other-timeline`) — не дольше `tokenTtlMs`, затем как без токена. Реплика с другой линией не считается догнавшей, даже если её позиция численно больше позиции токена: на новой линии те же номера означают другие записи (проверено).
- **Токен «из будущего»** (позиция впереди мастера той же линии: мастер восстановлен из копии, токен подделан ключом) — мастер, `token-ahead-of-primary`, не дольше `tokenTtlMs`.
- **Адрес мастера после failover** — забота вызывающего. Маршрутизатор читает «мастер» из настройки. Если там старый мастер, токены новой линии на нём дают `token-other-timeline`.
- Запись, потерянная при failover (была на старом мастере, не дошла до нового), не восстанавливается. Пакет не делает потерю видимой, но и не подсовывает вместо неё данные с реплики другой линии.

## Права роли зонда

Зонду нужна роль с членством в `pg_monitor` или хотя бы `pg_read_all_stats`. Без этого `pg_stat_wal_receiver.received_tli` пуст (замер на Postgres 17 под ролью без прав), линия времени реплики не определяется, и **каждая реплика исключается** как `no-stats-privilege`, а все чтения уходят на мастер. Причина названа отдельно, чтобы «все на мастере» не выглядело исправной работой. `system_identifier`, позиции, раскладка WAL (`pg_control_init()`) и состояние паузы роли без прав видны.

## Метрики

`router.stats()` возвращает чтения с реплик и мастера (доля), счётчики `ROUTE_REASON` и `EXCLUSION_REASON`, зонды ok/failed, последнее измеренное отставание каждой реплики в байтах (число; `null` — ещё не измерено), число просроченных токенов и итоги `confirm`. Объект сериализуется `JSON.stringify` как есть (до 0.2.0 отставание было `bigint`, и сериализация падала). Хуки `observer.routed` (каждое решение), `observer.probed` (каждый зонд с длительностью), `observer.tokenUnresolved` и `observer.confirmed` нужны для своих гистограмм и логов. Исключение в хуке, бросающий геттер свойства хука (прокси, ленивый объект метрик) и отказ `async`-хука маршрутизацию и процесс не роняют: у промиса, который вернул хук, отказ глушится (без этого он был бы `unhandledRejection`, то есть падением процесса).


```ts
import { ReplicaRouter } from '@hoshinotatsuya/pg-replica-sync';

const key = process.env.REPLICA_TOKEN_KEY;
if (key === undefined) {
  throw new Error('REPLICA_TOKEN_KEY is not set');
}
const observed = new ReplicaRouter<Pool>({
  primary: { name: 'primary', connection: 'postgres://app@primary/app', target: primaryPool },
  replicas: [{ name: 'r1', connection: 'postgres://app@replica-1/app', target: replica1Pool }],
  secrets: [key],
  waitForCatchUpMs: 20, // wait up to 20 ms for a lagging replica before falling back to the primary
  observer: {
    routed: (decision) => console.log('route', decision.role, decision.reason, decision.excluded),
    probed: (event) => console.log('probe', event.node, event.outcome, event.durationMs),
  },
});
// Plain numbers, safe for JSON.stringify: reads per role, reasons, exclusions, probes, lag per replica.
setInterval(() => console.log(JSON.stringify(observed.stats())), 60_000);
```

## Вместе с pg-runtime

Отдельного входа нет: маршрутизатор возвращает `target`, а транзакцию открывает вызывающий.

```ts
// read: a read-only transaction on the chosen node
const { target } = await router.route(token);
await transactionKeepingFailure(target, work, { readOnly: true });

// write: on the primary; the token after the transaction returned (COMMIT is done), any primary connection
await transactionKeepingFailure(primaryDb, work);
const next = await router.issueToken(primaryPool);
```

## Проверка

`pnpm test` поднимает **настоящую потоковую репликацию** (`scripts/with-replication.sh`): мастер (с архивом WAL в общем томе) и три реплики postgres:17-alpine (`PG_TEST_IMAGE` — другой образ, проверены 15, 16 и 18) в своей docker-сети, `pg_basebackup -R` с физическим слотом на каждую, каскадная реплика (от первой) и реплика только через архив WAL, и pgbouncer в режиме transaction над первыми двумя репликами (PgBouncer 1.26.1, образ закреплён digest `edoburu/pgbouncer@sha256:8638aa563607256d3c7440437534195f1066a92b68015d89ae9d6b935b444a6d`; другой — `PG_BOUNCER_IMAGE`). Контейнеры и сеть убираются в trap. Роль приложения `app` (pg_monitor, без суперправ) — для маршрутизатора и чтений. Пауза, задержка воспроизведения, остановка приёмника WAL и промоция делаются суперпользователем. Третья реплика расходная: её промотирует спека failover. Спеки меняют общую топологию (пауза реплик), поэтому группы идут в одном воркере (`JEST_GROUP_WORKERS=1`). Каждая спека имеет свой потолок времени; соединения, которые спека открыла со своим `application_name`, в конце обрываются на сервере, так что код, забывший их закрыть, краснеет утверждением, а не держит прогон.

Что доказано на настоящей репликации:
- запись → немедленное чтение с токеном видит запись (40 раз подряд, куда бы ни ушло);
- реплики на паузе — мастер, после resume и догоняния — снова реплика, и запись там видна;
- одна реплика отстаёт (`recovery_min_apply_delay`, не пауза) — каждое из 10 чтений идёт на догнавшую, а отставшая запись действительно не видит;
- ожидание догоняния уходит на реплику, догнавшую во время ожидания; потолок ожидания даёт мастер, а не зависание; медленная реплика и замёрзший мастер — `route()` в `waitForCatchUpMs + probeTimeoutMs` (+200 мс запаса);
- без токена: отставание больше потолка (+16 МБ через `pg_switch_wal`) — мастер, но только после потолка кэша, и ровно 3 зонда;
- недоступная реплика (закрытый порт) и реплика за замёрзшим `FaultProxy` исключаются по потолку зонда; повторно в окне отказа не опрашиваются; после `thaw` возвращаются;
- роль без `pg_read_all_stats` — каждая реплика исключена как `no-stats-privilege`;
- токен, выданный на реплике (узел в recovery), — «только мастер»; мусор, обрезанный токен, чужой ключ — `token-invalid`; чужой кластер — `token-foreign`; позиция из будущего — `token-ahead-of-primary`, в том числе когда в кэше старое состояние мастера; свежий законный токен при кэше мастера старше токена — `no-replica-eligible`, а не «впереди мастера»;
- `pg_promote()` — узел исключается как `promoted`; токен новой линии при реплике старой линии с большей позицией — мастер (`token-other-timeline`);
- токен, запрошенный внутри незакоммиченной транзакции с записью, — «только мастер», после COMMIT на том же соединении — с позицией; `commitAndIssueToken` — запись видна на реплике по токену; COMMIT транзакции с ошибкой — `TransactionNotCommittedError`, записи нет; пул, обёртка над пулом и соединение без `BEGIN` — `TransactionNotOpenError`, транзакция записи остаётся открытой, а после COMMIT настоящего клиента запись видна;
- `synchronous_commit = off`: каждый из 50 токенов не меньше позиции вставки сразу после COMMIT;
- простаивающий мастер сразу после `pg_switch_wal`: токен без новой записи реплика проходит за 3 с;
- 200 чтений с токеном впереди отставших реплик — по одному зонду каждой реплики и мастера, и при часах читателя на 5 с позади или впереди; новый токен после своей записи — свежий зонд каждой реплики на каждое чтение; 20 одновременных чтений — по одному зонду;
- «другая линия времени», «другой кластер», «впереди мастера» — мастер ровно `tokenTtlMs`, на миллисекунду позже — реплика без токена; «впереди мастера» истекает и под потолком частоты — по одному свежему зонду мастера после первой встречи с позицией, дальше кэш (50 из 50, 2 зонда мастера); другая линия времени при кэше мастера, снятом до первой встречи, — истекает тем же чтением по свежему зонду; «только мастер» не стареет и через час, хотя реплика с задержкой применения в потолке отставания; просроченный токен своей линии проверяется по позиции;
- соединение зонда оборвано сервером — следующее решение по свежему зонду, а не по кэшу; приёмник WAL реплики остановлен — чтение с токеном на эту реплику, а маршрутизатор без прежнего знания — `timeline-unknown`; за тем же адресом другой сервер — прежняя линия времени не переносится;
- pgbouncer в режиме transaction над догнавшей и отставшей репликой: транзакции одного клиента попадают на оба сервера; `confirm` первым запросом в читающей транзакции — каждое из 20 подтверждённых чтений видит запись, отставший сервер отклонён;
- балансировщик по кругу над догнавшей и отставшей репликой: каждое из 10 чтений с `confirm` видит запись, отставший сервер отклонён, и отказы видны в `stats().confirms` и хуке с причиной; отказ и молчание соединения чтения — «нет» с причиной `unavailable` и ошибкой; экземпляр сервера одинаков при разных DateStyle и TimeZone сессии;
- каскадная реплика (реплика реплики) воспроизвела токен — чтение на неё, запись видна; реплика только через архив WAL воспроизвела позицию токена — всё равно исключена как `timeline-unknown` (линию времени без приёмника WAL роль зонда не видит), с токеном и без;
- законный свежий токен НЕ истекает: часы читателя ±120 с, `tokenTtlMs` 1 и 200, кэш мастера снят до записи (читатель прогрет чтением без токена), зонд мастера начат до записи и ещё идёт — по 20 чтений в каждом из 8 сценариев, каждое на мастер, запись видна, `expiredTokens` 0 (реплики с задержкой применения в потолке отставания: истечение увело бы чтение без записи); двойник — токен и правда впереди мастера — истекает;
- 2000 разных токенов на 100 позиций дважды по кругу — ровно по 100 зондов каждой реплики; горячая позиция среди 2048 новых — ни одного лишнего зонда, новая позиция — один;
- медленная живая реплика (150 мс на кусок: установка соединения дольше потолка зонда 600 мс, запрос короче) — после первого отказа годится; замёрзшая — `unavailable` во всех 10 попытках, соединение рвётся по `connectTimeoutMs` и открывается заново;
- часы кэша по умолчанию: кэш живёт `stateTtlMs` и истекает; часы кэша шагнули на час назад — пауза реплики замечена следующим чтением;
- после `close()` решение «реплика», полученное раньше, — `confirm` = `false` без запроса;
- потолок зонда соединение не рвёт, а по `connectTimeoutMs` рвётся ИМЕННО старое соединение — запрос на новом в этот момент проходит; после `close()` соединение не открывается; `close()` во время ожидания догоняния прерывает его, и соединений зонда на серверах не остаётся.
